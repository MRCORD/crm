# Twenty CRM Database & System Architecture

This document provides a comprehensive technical breakdown of the database architecture, metadata engine, and runtime data layer in **Twenty CRM** (`twentyhq/twenty`), based directly on its production codebase and engineering documentation.

---

## 1. Architectural Overview & Design Philosophy

Traditional web applications model data with static schemas and compile-time ORMs (e.g., standard TypeORM, Prisma, Hibernate). This approach breaks down for customizable business software like a CRM because:
1. Users need to define **Custom Objects** (tables) and **Custom Fields** (columns) dynamically at runtime without restarting the server or triggering code recompilations.
2. Different organizations (workspaces) require **strict tenant isolation** while sharing compute and database resources.
3. Every database operation requires automatic enforcement of **Row-Level Security (RLS)**, field-level permissions, soft deletion, and real-time database event emission for workflows and webhooks.

Twenty solves this by implementing a **hybrid multi-tenant, metadata-driven architecture** over **PostgreSQL** powered by a custom engine named **TwentyORM**.

```
PostgreSQL Database
│
├── core (Schema - Shared System & Metadata)
│   ├── Tenant & Auth: workspace, user, userWorkspace, session, apiKey, role
│   ├── Application Registry: application, featureFlag
│   └── Metadata Catalogs (Source of Truth for Schemas):
│       ├── objectMetadata (table definitions)
│       ├── fieldMetadata (column definitions)
│       ├── indexMetadata (database indexes)
│       └── view, pageLayout, commandMenuItem, workflow
│
├── workspace_<base36_workspace_id_1> (Isolated Tenant Schema)
│   ├── Standard Tables: person, company, opportunity, note, task...
│   ├── Custom Tables:   _deal, _property, _equipment...
│   └── Junction Tables: noteTarget, taskTarget, calendarEventTarget...
│
└── workspace_<base36_workspace_id_2> (Isolated Tenant Schema)
```

## 2. PostgreSQL Multi-Tenancy: Schema-per-Workspace

Twenty isolates tenant data using **one PostgreSQL schema per workspace**.

* **Schema Naming Convention:**
  Each workspace is assigned a schema name generated by prefixing `workspace_` to the base-36 representation of the workspace UUID:
  ```typescript
  // packages/twenty-server/src/engine/workspace-datasource/utils/get-workspace-schema-name.util.ts
  export const getWorkspaceSchemaName = (workspaceId: string): string => {
    return `workspace_${uuidToBase36(workspaceId)}`;
  };
  ```
* **Table Naming Convention:**
  * **Standard Objects:** Named directly by their singular name (e.g., `person`, `company`, `opportunity`, `note`, `task`).
  * **Custom Objects:** Prefixed with an underscore `_` to prevent collisions with future standard objects (e.g., `_myCustomObject`, `_deal`).

### Trade-offs of the Schema-per-Tenant Approach

| Dimension | Schema-per-Tenant (Twenty's Choice) | Shared Table + `workspace_id` | Database-per-Tenant |
| :--- | :--- | :--- | :--- |
| **Data Isolation** | High (isolated PostgreSQL namespaces) | Weak (accidental omitted `WHERE` leaks data) | Complete (separate databases) |
| **Dynamic DDL** | Simple (`ALTER TABLE` affects only 1 tenant) | Complex / dangerous (locks table for all tenants) | Simple |
| **Connection Pooling** | Shared pools (`pg.Pool`) across schemas | Shared pools | Pool exhaustion per DB |
| **Backup / Restore** | Granular (`pg_dump -n workspace_xyz`) | Difficult without complex SQL exports | Simple (`pg_dump db_name`) |
| **Schema Migrations** | Requires running migrations across $N$ schemas | Single migration command | Requires running across $N$ DBs |

*(Note: Prior to version 0.54, Twenty maintained separate `core` and `metadata` schemas. All metadata catalogs have since been merged into the `core` schema).*

## 3. Metadata Engine & Dynamic Schema Catalog

All workspace schemas are defined declaratively in the `core` schema tables.

### 3.1. `core.objectMetadata`
Represents an object (table) within a workspace:
* `id` (UUID): Primary key.
* `workspaceId` (UUID): FK to `core.workspace`.
* `nameSingular` & `namePlural` (e.g., `"company"`, `"companies"`).
* `labelSingular` & `labelPlural` (e.g., `"Company"`, `"Companies"`).
* `targetTableName`: Name of the physical table in Postgres (`company` or `_customDeal`).
* `isSystem` & `isActive`: Flags determining visibility and system immutability.
* `readability` & `writability`: Access control tier (`OPEN`, `INHERITED`, `PRIVATE`, `SYSTEM`, `APPLICATION`).
* `duplicateCriteria` (JSONB): Unique fields used for duplicate detection during CSV imports and API sync.

### 3.2. `core.fieldMetadata`
Represents an individual field (column) belonging to an `objectMetadata` record:
* `id` (UUID): Primary key.
* `objectMetadataId` (UUID): FK to `core.objectMetadata`.
* `name`: Column identifier (e.g., `"annualRevenue"`, `"emails"`).
* `label`: Human-readable label.
* `type`: Enum of `FieldMetadataType` (e.g., `TEXT`, `NUMERIC`, `CURRENCY`, `EMAILS`, `TS_VECTOR`).
* `defaultValue` (JSONB): Serialized default value.
* `isNullable`: Whether the database column permits `NULL`.
* `settings`: JSONB configuration (e.g., options for `SELECT` fields, relation types).

### 3.3. Syncable Entity Architecture
All metadata entities extend `SyncableEntity`, which provides:
* `universalIdentifier` (UUID): Deterministic UUID maintained across environments (staging, production, self-hosted).
* `applicationId` (UUID): References the application package owning the metadata (e.g., `TWENTY_STANDARD_APPLICATION` or a third-party app).

## 4. Invariant System Fields

Every table created inside a workspace schema automatically receives 8 universal system fields:

| Field Name | Type | Physical Column Type | Description |
| :--- | :--- | :--- | :--- |
| `id` | `UUID` | `uuid PRIMARY KEY DEFAULT gen_random_uuid()` | Immutable primary key |
| `createdAt` | `DATE_TIME` | `timestamptz DEFAULT now()` | Record creation timestamp |
| `updatedAt` | `DATE_TIME` | `timestamptz DEFAULT now()` | Last update timestamp |
| `deletedAt` | `DATE_TIME` | `timestamptz NULL` | Timestamp for soft deletion |
| `createdBy` | `ACTOR` | Composite Columns | Actor who created the record |
| `updatedBy` | `ACTOR` | Composite Columns | Actor who last modified the record |
| `position` | `POSITION` | `float8 DEFAULT 0` | Fractional position for ordering in views |
| `searchVector` | `TS_VECTOR` | `tsvector GENERATED ALWAYS AS (...) STORED` | Postgres Full-Text Search column |

## 5. Field Types & Physical Column Decomposition

Instead of storing complex domain types as opaque JSON blobs (which prevent indexing, constraint checking, and efficient SQL aggregations), Twenty decomposes rich types into **discrete physical columns**.

```
High-Level Field: annualRevenue (CURRENCY)
          │
          ├─► annualRevenueAmountMicros (numeric)
          └─► annualRevenueCurrencyCode (text)

High-Level Field: address (ADDRESS)
          │
          ├─► addressStreet1 (text)
          ├─► addressStreet2 (text)
          ├─► addressCity (text)
          ├─► addressPostcode (text)
          ├─► addressState (text)
          ├─► addressCountry (text)
          ├─► addressLat (numeric)
          └─► addressLng (numeric)

High-Level Field: createdBy (ACTOR)
          │
          ├─► createdBySource (enum: MANUAL, API, WORKFLOW...)
          ├─► createdByWorkspaceMemberId (uuid)
          ├─► createdByName (text)
          └─► createdByContext (jsonb)
```

### Type Mapping Table

| `FieldMetadataType` | Physical PostgreSQL Column Type | Notes |
| :--- | :--- | :--- |
| `UUID` | `uuid` | Primary keys and foreign keys |
| `TEXT` | `text` | Unbounded strings |
| `NUMERIC` | `numeric` | Arbitrary-precision numbers |
| `NUMBER`, `POSITION` | `float8` / `float` | Sorting positions, metrics |
| `BOOLEAN` | `boolean` | Flags |
| `DATE` | `date` | Date-only values (`YYYY-MM-DD`) |
| `DATE_TIME` | `timestamptz` | ISO 8601 timestamps with timezone |
| `SELECT`, `RATING` | `enum` | PostgreSQL `CREATE TYPE ... AS ENUM` |
| `MULTI_SELECT` | `enum[]` | Array of PostgreSQL enum values |
| `RAW_JSON`, `FILES` | `jsonb` | Structured configuration and attachments |
| `TS_VECTOR` | `tsvector` | PostgreSQL generated full-text search column |
| `CURRENCY` | `numeric` + `text` | Flattened into `...AmountMicros` + `...CurrencyCode` |
| `FULL_NAME` | `text` + `text` | Flattened into `...FirstName` + `...LastName` |
| `ADDRESS` | 8 columns (`text`, `numeric`) | Street, City, State, Postcode, Country, Lat, Lng |
| `ACTOR` | 4 columns (`enum`, `uuid`, `text`, `jsonb`) | Source, WorkspaceMemberId, Name, Context |

## 6. Relationships & Polymorphism via Junction Objects

### 6.1. One-to-Many / Many-to-One
* Implemented using standard relational foreign keys.
* The owning table holds a physical column named `<fieldName>Id` (e.g. `companyId UUID REFERENCES "workspace_...".company(id) ON DELETE SET NULL`).

### 6.2. Polymorphic CRM Associations
CRMs require associating activities (notes, tasks, calendar events) with multiple entities simultaneously (e.g. a Task linked to both a Person and an Opportunity).
Rather than using generic string columns (`target_type`, `target_id`) which break foreign key integrity and prevent database-level cascading, Twenty uses **explicit junction tables**:

* `noteTarget`: Columns `noteId`, `targetPersonId`, `targetCompanyId`, `targetOpportunityId`.
* `taskTarget`: Columns `taskId`, `targetPersonId`, `targetCompanyId`, `targetOpportunityId`.
* `calendarEventTarget`: Columns `calendarEventId`, `targetPersonId`, `targetCompanyId`, `targetOpportunityId`.
* `messageThreadTarget`: Columns `messageThreadId`, `targetPersonId`, `targetCompanyId`, `targetOpportunityId`.

Every foreign key has an explicit `ON DELETE CASCADE` constraint.

## 7. TwentyORM: The Dynamic Data Access Layer

Because database schemas mutate at runtime, Twenty cannot use TypeORM's static decorator entities (`@Entity`, `@Column`) for tenant data. Instead, it built **TwentyORM**:

```
Application Call:
workspaceOrmManager.getRepository('company').find({ where: { name: 'Acme' } })
                                │
                                ▼
1. Load Context & Metadata from Cache (Redis / Memory)
   - FlatObjectMetadataMaps
   - FlatFieldMetadataMaps
   - Permissions, RLS Predicates & Feature Flags
                                │
                                ▼
2. Derive WorkspaceTableShape
   - Map high-level fields -> physical column names
   - Map composite properties -> physical column names
   - Map relations -> joinColumnName & targetTable
                                │
                                ▼
3. Build SQL via WorkspaceSelectQueryBuilder
   - Inject Row-Level Security (RLS) predicates
   - Inject record-sharing checks (recordShare table)
   - Inject soft-delete filter: "deletedAt IS NULL"
                                │
                                ▼
4. Execute Parameterized Query via pg.Pool (node-postgres)
                                │
                                ▼
5. formatResult: Reconstruct Domain Objects
   - Group composite columns back into nested objects
   - Parse enums and JSON fields
                                │
                                ▼
6. (On Mutation) Emit Database Batch Events (CREATED, UPDATED, DELETED)
```

### Key Components of TwentyORM

* **`WorkspaceOrmManager`:** Entry point for obtaining repositories per workspace (`getRepository('person')` or `getRepository(PersonEntity)`).
* **`WorkspaceDataSource`:** Encapsulates the active `pg.Pool` connection and metadata context. Supports primary/read-replica routing and transaction isolation.
* **`WorkspaceTableShape`:** Cached blueprint of an object's physical table layout, columns, composite sub-columns, and join relationships.
* **`formatData` & `formatResult`:** Symmetrical transformation pipeline:
  * `formatData`: Flattens `{ annualRevenue: { amountMicros: 1000, currencyCode: 'USD' } }` into `{ annualRevenueAmountMicros: 1000, annualRevenueCurrencyCode: 'USD' }`.
  * `formatResult`: Recomposes flat SQL result rows back into domain models for consumers.
* **Row-Level Security (RLS) Engine:** Query builders inspect user permissions and automatically append SQL `WHERE` clauses matching role permissions and record-sharing rules.

## 8. Dynamic Migrations & DDL Execution Engine

When a workspace schema changes (e.g. user adds a field or object in UI, installs an app, or standard objects are updated), Twenty executes a **two-phase declarative migration**:

```
           Workspace Migration Orchestrator
                          │
         ┌────────────────┴────────────────┐
         ▼                                 ▼
   State: "from"                     State: "to"
 (Current Metadata)               (Target Metadata)
         └────────────────┬────────────────┘
                          ▼
            Diff & Action Generation:
    • UniversalCreateObjectAction
    • UniversalCreateFieldAction
    • UniversalCreateIndexAction
                          │
         ┌────────────────┴────────────────┐
         ▼                                 ▼
    Phase 1: Metadata                Phase 2: Workspace DDL
   Insert rows into:                Execute SQL DDL in:
   core.objectMetadata              workspace_<id>."tableName"
   core.fieldMetadata               via WorkspaceSchemaManager:
                                    • createTable()
                                    • addColumn()
                                    • createEnum()
                                    • createIndex()
```

### Safety & Upgrade Guardrails
* **`WORKSPACE_SCHEMA_DDL_LOCKED`:** Global configuration switch that halts tenant DDL operations during server version upgrades.
* **Rollback-Safe Transactions:** Schema operations run within strict PostgreSQL transactions; if DDL fails, metadata mutations are rolled back.
* **SQL Injection Prevention:** Identifiers are sanitized through `escapeIdentifier()` and types through strict allowlists.

## 9. Dynamic GraphQL and REST APIs

Twenty does not require developers to handwrite endpoints for custom objects.

### Dynamic GraphQL (`WorkspaceSchemaFactory`)
1. Reads `flatObjectMetadataMaps` and `flatFieldMetadataMaps` from cache.
2. Compiles a GraphQL Schema Definition Language (SDL) string in memory.
3. Builds dynamic resolvers via `WorkspaceResolverFactory` (`findMany`, `findOne`, `createOne`, `updateOne`, `deleteOne`, etc.).
4. Combines them using `@graphql-tools/schema`'s `makeExecutableSchema()`.

### Dynamic REST API (`RestApiCoreController`)
* Exposes generic wildcard endpoints:
  * `GET /rest/:objectName`
  * `POST /rest/:objectName`
  * `PATCH /rest/:objectName/:id`
  * `DELETE /rest/:objectName/:id`
  * `POST /rest/:objectName/duplicates`
* Resolves `:objectName` to the workspace's `objectMetadata`, derives the `WorkspaceRepository`, and executes the operation via TwentyORM.

## 10. Summary of Architectural Decisions

| Requirement | Twenty CRM Implementation | Key Advantage |
| :--- | :--- | :--- |
| **Tenant Isolation** | PostgreSQL Schema per Workspace (`workspace_<base36_uuid>`) | Physical query boundaries, native DDL execution, independent tenant backups. |
| **Custom Schema Definition** | Declarative metadata tables in `core` (`objectMetadata`, `fieldMetadata`) | Database-driven schema updates without server restarts or recompilations. |
| **Rich Field Types** | Physical column flattening (e.g. `amountMicros` + `currencyCode`) | Full SQL indexing, native filtering, and aggregate operations (`SUM`, `AVG`). |
| **Polymorphic Links** | Concrete typed junction tables (`noteTarget`, `taskTarget`) | Referential integrity (`FOREIGN KEY`) and cascading deletes. |
| **Data Access** | Custom runtime query compiler (`TwentyORM`) over raw `pg.Pool` | Dynamic entity handling without TypeORM entity registry limitations. |
| **API Delivery** | Dynamic GraphQL schema compilation & wildcard REST routes | Zero code needed to expose full CRUD, filtering, and sorting for new entities. |
